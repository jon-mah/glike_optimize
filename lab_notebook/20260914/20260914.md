### VCF → VCZ
* **On first run through I encountered an error in which the allelics position of the output `.vcz` was not sequential, either due to duplicate site positions or an unsorted initial `.vcf.gz`. To address this, `bcftools sort` was used to sort the VCFs by genomic position.**
  * This is important because `bio2zarr` / downstream `tsinfer` processing requires variant positions to be in strictly increasing order.
* After sorting, the VCFs were converted to `bio2zarr` `.vcz` format.
    * Note: I encountered an out-of-memory error for **chromosomes 2 and 3** for the `array_5388` dataset. I have allocated 128Gb and 20 CPUs for each task, so hopefully things will run correctly.
* The `.vcz` files are now the intended input format for the `tsinfer` workflow.

## `snpArcher` / CCDG Standards

### Goal

* I have been setting up `snpArcher` to process the Native Hawaiian WGS data in a way that is consistent with the CCDG-style joint variant-calling workflow.
* The current test dataset consists of individual gVCF files rather than raw sequencing reads.
* The working project is:

  * `/project2/mahj_1946/MEC_WGS_NH_546_gvcf`
* The `snpArcher` workflow is being run with Snakemake on the USC cluster using SLURM. [16/26 internal jobs]
* Current software versions include:
  * `snpArcher 2.0.0-dev-6209bb5`
  * Snakemake 9.26.0
  * Python 3.11.4
  * Conda 25.11.0

### Samples / Input Setup

* I set up a `samples.csv` file using the individual gVCFs as the input.
* The sample sheet uses the `sample_id`, `input_type`, and `input` fields expected by `snpArcher`.
* The workflow recognizes the data as gVCF input.
* Because the inputs are gVCFs rather than raw FASTQs, `snpArcher` correctly reports that coverage statistics and coverage BED generation cannot be performed from the supplied inputs.
* **The current test contains 539 gVCF samples recognized by the workflow**.

### Troubleshooting

* Initially, there were problems getting the sample sheet/configuration recognized correctly.
  * The workflow uses `--deployment-method conda`.
  * There were issues involving the OpenJDK/Conda environment setup.
  * The Conda package/cache location was also initially being resolved incorrectly (`/project2/mahj_1946/snpArcher/~./conda/pkgs`).
  * These environment problems had to be separated from actual workflow failures.
* The reference setup was another problem.
  * The workflow is currently configured to use `MEC_NH_546` based on `GCA_000001405.29`.
  * `snpArcher` needed to create the reference indexes before the downstream workflow could proceed.
  * The `index_reference` rule initially failed while running `samtools faidx`, `samtools dict`, and `bwa index`.
* I then isolated the reference-indexing and GenMap steps to determine whether the failures were workflow/configuration problems or cluster-resource problems.
* The GenMap indexing step was subsequently identified as an explicit memory problem:
  * `genmap index` exited with status 137.
  * SLURM reported an `OOM_kill` event.
  * The job was killed because it exceeded the memory available to the job.
* I adjusted the resource requests and modified the GenMap indexing logic to use different indexing modes depending on the decompressed reference size:
  * default `divsufsort` for smaller references
  * sampled mode (`-S 20`) for larger references
  * skew mode (`-A skew`) for very large references.
* This has allowed me to get further into diagnosing the workflow rather than treating every failure as a generic `snpArcher` problem.
